# Документный академический proof-отчёт RICIS

## Назначение

`ProveDocument` строит Markdown-документ по структуре академического доказательства: заголовок, аннотация, доказательный статус, определения, аксиомы и внешние предпосылки, тезис, машинно воспроизводимая трассировка, производное expression tree и явно перечисленные границы результата.

Метод **не повышает** доказательный статус исходного `Prove`. Он лишь делает его границы проверяемыми и видимыми в самом документе. Условия, ограничения и аксиомы записываются как предпосылки, но не компилируются, не исполняются и не признаются библиотекой истинными.

## API

```csharp
var profile = new RicisProofDocumentProfile(
    title: "Условная теорема",
    scope: RicisProofScope.ConditionalTheorem,
    @abstract: "Краткое описание результата.",
    theorem: "При P1 и P2 следует C.",
    definitions: ["Определение объекта X."],
    axioms: ["P1: ...", "P2: ..."],
    limitations: ["Истинность P1 и P2 не проверяется."]);

var document = new StringBuilder();
var derived = equations.ProveDocument(constraints, claim, profile, document);
```

Поддержаны оба существующих proof-контракта:

| Overload | Производное дерево |
|---|---|
| `IEnumerable<Expression<Func<T,bool>>>.ProveDocument(...)` | Нормализованная unary-функция `Expression<Func<T,T>>`. |
| `IEnumerable<Expression<Func<double,double,bool>>>.ProveDocument(...)` | Равенство координаты поддерживаемой двухпеременной линейной системы. |
| `IEnumerable<Expression<Func<double,double,bool>>>.ProveTypeIdentityCriticalLine(...)` | Нормативное точное следствие ID-01–ID-06: первая координата отражённой пары равна `Divide(1,2)`. |

### Форматируемый DRY-overload

Помимо существующего академического `ProveDocument`, proof API поддерживает единый renderer для нескольких представлений:

```csharp
var document = new StringBuilder();
var derived = conditions.ProveDocument(
    constraints,
    claim,
    profile,
    RicisProofDocumentFormat.Json,
    text => "// generated by Ricis.Core\n" + text,
    document);
```

`Func<string, string>` получает **полностью отрендеренный документ** и возвращает точный текст, который будет добавлен в `StringBuilder`. Callback предназначен для добавления преамбулы, эпилога или организационного оформления. Он не получает доступ к expression tree и не может изменить производный RICIS-результат, scope или trace.

| `RicisProofDocumentFormat` | Шаблон | Статус |
|---|---|---|
| `Log` | Компактный line-oriented protocol с trace. | Диагностическое представление. |
| `Academic` | Полный Markdown-документ с определениями, scope, предпосылками, trace и границами. | Основной академический формат. |
| `Lean` | Для generic C# expression tree выполняет controlled rejection; корректный Lean output строится через `RicisLeanTemplate(StructuredData, RequestedRows) => RicisLeanDoc`. | LeanDoc компилируем только для поддержанного structured bridge ID-01–ID-06. |
| `Json` | Валидный структурированный JSON: profile, normative steps, trace и derived expression. | Машиночитаемое представление. |

Log, Academic и Json используют один уже построенный `Prove` derivation. Они не запускают дополнительные RICIS-фазы, не исполняют условия и не применяют `Eval`, Razor или TypeScript. Для Lean используется отдельный структурированный источник: `RicisLeanTemplate.Render(RicisLeanStructuredData, RicisLeanRequestedRows)` возвращает `RicisLeanDoc` с generated Lean source. Generic C# expression tree без поддержанного bridge отклоняется, а не превращается в comment scaffold. Это сохраняет DRY: proof engine и Lean structured model существуют в одном месте, а остальные templates отвечают только за presentation.

## Доказательный статус

| Статус | Значение | Чего он не означает |
|---|---|---|
| `FiniteDerivation` | Воспроизводимое преобразование конкретных переданных expression tree. | Истинность общих аксиом, внешних данных или кванторного утверждения. |
| `ConditionalTheorem` | Заключение следует из явно перечисленных формальных предпосылок. | Что библиотека доказала сами предпосылки или любую более сильную внешнюю теорему. |

> Количество успешно пройденных тестов измеряет покрытие реализованных ветвей кода и устойчивость к известным регрессиям. Оно не является доказательством истинности внешней математической аксиомы, не проверяемой этими тестами.

## Структура сформированного документа

| Раздел | Содержимое |
|---|---|
| Аннотация | Заявленная цель документа. |
| Доказательный статус | Конечное выведение либо условная теорема. |
| Определения | Пользовательские определения, нужные для чтения предпосылок. |
| Аксиомы и внешние предпосылки | Явно названные элементы, истинность которых не проверяется API. |
| Теорема или конечный тезис | Формулировка цели. |
| Машинно воспроизводимое символическое выведение | Вложенный протокол действительных RICIS-шагов. |
| Воспроизводимый результат | Итоговое expression tree. |
| Границы и непроверенные утверждения | Исключённые из статуса доказательства заявления. |

Нормативные фазы и промежуточные SP2-деревья формируются существующим `Prove`; `ProveDocument` не создаёт вымышленных алгебраических шагов.

### Именованные нормативные шаги

`RicisProofDocumentProfile.NormativeSteps` принимает `RicisProofAxiomStep` с идентификатором, названием и точным следствием. Они печатаются отдельным разделом до expression-tree трассировки. Специализированный `ProveTypeIdentityCriticalLine` использует этот механизм для обязательной последовательности ID-01–ID-06 и не принимает уравнения ID-02/ID-04 как внешние безымянные `P1`/`P2`.

## Ограничения текущего ядра

Текущий документный слой точно документирует поддержанные scalar-выражения, две линейные координаты и полную нормативную цепочку ID-01–ID-06 для отражённой пары. Дополнительные комплексные символы `s`, `ζ(s)`, `ξ(s)` и кванторные конструкции могут быть добавлены отдельным расширением proof-языка; их отсутствие не изменяет замкнутый вывод ID-01–ID-06, уже представленный в C# и Lean.
